# 탐색 교사 전환 목록

2026-10-28. 강한 탐색 교사를 먼저 만들고, 검증된 판단을 이후 신경망에 학습시키는 방향이다.

## 정리 반영

브랜치: `phoenix`.

- workspace는 `augment-core`·`augment-search`·`augment-app` 세 crate로 줄였다.
  앱은 `web`·`play`·`snapshot` 세 실행 파일을 제공하고 진입점과 구현을 분리했다.
- V2/V3/V4 신경망·ONNX·학습·승격·기존 데이터/fixture 계약과 전용 CLI를 삭제했다.
- 독립 MCTS V5의 작은 게임·belief·실제 카드 프로파일·journal 실험 구현을 삭제했다.
  필요한 정보 접근 원칙은 [관측 원칙](observation-safety.md)으로 남겼다.
- 기존 AND-OR Solver는 `augment-search::tactics`로 옮겼다. 행동 인덱스·인코더·모델 의존성을
  제거하고 엔진 `Action`을 직접 반환한다. 확률·알려진 대상 누락·예산 부족은 미확인이다.
- 이전 세대 전용 설계·학습 실험 결과·승격 안내와 검증 스크립트를 삭제했다.
  실제 엔진의 규칙 스냅숏·원본·회귀 테스트·최적화 측정·웹 기능은 유지한다.
- Python 의존성 파일과 ONNX/CUDA·학습 전용 Rust 의존성을 제거했다.
  기본 검증은 Cargo·Node·PowerShell만 사용한다.

전환 검증: Rust 242개 테스트(compile-fail 문서 테스트 포함), workspace Clippy·fmt,
오프라인 웹 검사 4개, 전술 진단 2개 국면, 원본 포 helper 3개 대조가 통과했다.
세 crate 통합 후 같은 검증을 다시 통과했고, `web`·`play` 실행과 `snapshot` 동일 카탈로그
비교를 확인했다. 실제 HTTP의 health/state 및 정적 파일 6개 경로도 이동한 원본과 일치했다.
기력 우위나 전체 사이트 정합성의 증거는 아니다.

로컬 ignored 모델·실험 산출물·가상환경은 소스 삭제 목록과 별개다.
이전에 V2 ONNX 바이너리의 삭제는 자동 승인 검토에서 차단됐고 이 파일은 남아 있다.

## P1 결과

### P1-1 전술 검사 — 완료

`tactics.rs`가 `[CLEANUP, HYPOCRISY]`를 하드코딩해 거부하던 것을 `KNOWN_INCOMPLETE_TARGET_CARDS`
(빈 목록)로 정리했다. P0-1에서 두 카드의 열거를 고쳤는데 전술 검사에 반영되지 않았던 것이다.

추가한 테스트:
- 재료 평가가 손해라고 보는 국면에서 강제 승리를 찾는가
- 카드가 만든 위협이 상대 방어로 반박되는가
- 생성기가 낸 모든 선언을 검증기가 받아들이는가 (아래 버그 참조)

### P1-1에서 발견한 `premove` 버그

벤치마크 `seed 3`이 `프리 무브의 목표 칸으로는 이동할 수 없습니다`로 실패했다. 원인은 생성기와
검증기의 불일치였다:

- 생성기는 **첫 수가 적용된 보드**에서 두 번째 수를 열거한다
- 검증기는 모든 쌍을 **원래 보드**로 검사했다

그래서 생성기가 낸 2·3수 선언을 검증기가 거부했다. `play`가 단계별로 보드를 갱신하며 검증하도록
고쳤다. 최적화와 무관한 기존 버그다.

### P1-2 평가 — 전술 이득 없음, 대국 이득 있음

`Evaluation::{Material, Positional}`을 추가했다. `Positional`은 재료에 다음을 더한다:

- 왕권 안전: 상대 킹 주변 5×5에 있는 아군 기물 수
- 카드 자원: 미사용 charge와 설치된 passive
- 활동성: 실제 열거된 합법 행동 수(상한 있음), 행동이 0이면 페널티

#### 전술: 이득 없음

3 seeds × 8 시나리오, 동일 200ms 비교:

| 항목 | 값 |
|---|---|
| 액션 일치 | 24 중 18 |
| positional이 **더 깊게** 간 경우 | **0** |
| 더 얕게 간 경우 | 3 |
| 동일 | 21 |

#### 평가 비용을 먼저 고쳐야 했다

첫 구현은 활동성을 **실제 합법 행동 열거**로 계산했다. leaf마다 열거하니 평가가 재료의 38배
(8.5ms → 327ms)가 되었고, 그 비용 때문에 노드와 깊이가 함께 줄었다. 깊이는 활동성 정확도보다
가치가 크므로 이는 나쁜 거래다.

fingerprint 캐시를 시도했으나 `fingerprint()`가 전체 상태를 해시해 더 느려졌다(548ms).

최종 구현은 **기물 배치 기반 근사**다. sliding 기물은 광선 길이, leaper는 상수로 활동성을
계산한다. 열거가 없어 leaf마다 O(기물 수)다.

| 구현 | 평가 시간 | 깊이 합 |
|---|---:|---:|
| 재료 | 9.2ms | 24 |
| 열거 활동성 | 327ms | 24 → 20 |
| fingerprint 캐시 | 548ms | 20 |
| **배치 근사** | **44.3ms** | **22** |

#### 대국: 이득 없음

수정된 구현으로 Arena `--against` 모드에서 두 평가를 대국시켰다(150ms, 색상 교환, 12판 중
결정 11판):

| 항목 | 값 |
|---|---|
| positional 승 | 4 |
| material 승 | 4 |
| 무승부 | 3 |
| **positional 점수율** | **0.50** |

**이득이 없다.** 앞서 측정한 0.70은 열거 비용 때문에 positional의 깊이가 줄어든 부작용이
만든 값이었고, 비용을 고치자 사라졌다. 그 측정은 잘못된 구현을 잰 것이었다.

기본값은 `Material`로 유지한다. `--evaluation positional`로 선택할 수 있고, 벤치·아레나
리포트는 실제 사용한 평가를 기록한다.

P1-2의 완료 판단("재료 기준선 대비 동일 시간 전술/대국 개선")은 **두 축 모두 미충족**이다.
추가 항목이 깊이도 대국 성적도 개선하지 못했다. 다만 평가 비용을 38배 줄인 것은 남는 이득이며,
이후 다른 항목을 시도할 때 같은 함정을 피할 수 있다.

### P1-3 탐색 교사 Arena — 완료

`crates/augment-search/src/arena.rs`와 `arena` 서브커맨드를 추가했다. 요구사항을 다음과 같이
지켰다:

| 요구 | 구현 |
|---|---|
| 같은 규칙 | 양쪽이 같은 엔진·같은 검색 설정 |
| 같은 정보 | 같은 `GameState`에서 번갈아 수를 고름 |
| 같은 시간 | `SearchConfig` 하나를 공유, 진영별 재정의 없음 |
| 색상 교환 | 페어링마다 White/Black 양쪽으로 한 판씩 |
| 승패·미완주·오류·초과 별도 보고 | `Outcome::{Decided, Truncated, Error, Overrun}` |

`ArenaSummary`는 **결정된 대국만** 점수율에 넣는다. 미완주·오류·초과는 각각 따로 세고 `notes`에
남긴다. 이렇게 해야 멈추거나 죽는 하네스가 강해 보이지 않는다. 결정된 대국이 0이면 점수율이
추정치가 아님을 명시한다.

`winner`는 색이 아니라 **설정** 기준(`Winner::{First, Second}`)으로 기록한다. 색을 교환하므로
같은 설정이 White로 이기든 Black으로 이기든 둘 다 `First`다. 이것이 페어링을 넘어 비교 가능하게
만든다.

구현 중 테스트가 잡은 결함 두 개:
- 초과 판정이 결정된 대국까지 `Overrun`으로 덮어써 결과를 지웠다. 검색은 자기 마감에서 멈추고
  현재 노드를 마저 끝내므로 1ms 미만 초과는 정상 동작이다. 허용치 25ms를 두어 해결했다.
- `winner`가 색 기준이라 집계가 항상 틀렸다. 설정 기준으로 바꿨다.


## P0-2 결과: 전이 대조는 두 층으로 닫혔다

### 술어 층 — 원본 대조 완료

`scripts/test-snapshot-transitions.mjs`가 **1102 번들 자체를 실행**해 15개 술어를 검증한다.
15개 술어, 40개 단정이며 `verify-search.ps1`에 연결돼 있다.

| 영역 | 검증한 술어 |
|---|---|
| 카드 잠금 | `usesTurnEndingTrojan`, `isWorkerCardPendingNextTurn`, `authoritativeCardsUsedThisTurn`, `normalizeCardsUsedThisTurn` |
| 후속 phase | `ownerStartDuePly`, `ownerStartsRemaining`, `retainV6Turn` |
| 확률 | `workerStableIndex`, `stableHash`, `stableIndex`, `stableShuffle` |
| 종료 | `usesOctober27Balance`, `usesNovemberExpansion`, `usesRulesAtLeast`, `usesV13Rules` |

자기완결적 술어만 pin한다. 의존이 해시 상수뿐인 것들이라 어댑터가 작게 유지되고, 단정이
실제 번들 코드로 판정된다.

### 카드 사례 층 — 어댑터 비용 때문에 범위 밖

전이 계약이 바뀐 17장의 **카드 전이 함수를 실행해 대조하는 것**은 불가능하다. 측정값:

| 대상 | 필요한 어댑터 선언 |
|---|---:|
| 기존 오라클 9개 전체 이관 | **36,600** |
| 카드 dispatcher 7개 (`applyOctober13Card` 등) | 각 **4,001+** (측정 상한) |

번들의 절반을 복제해야 하고, 그러면 "번들로 번들을 검증"하는 순환이 된다. 대신
`crates/augment-core/tests/card_definitions.rs`가 17장의 계약이 카탈로그 선언과 일치하는지
검증한다. 이는 원본 대조가 아니라 **카탈로그 대조**이며, 그 구분을 명시한다.

카드 수준 `END_TURN` 동작은 Rust 테스트가 직접 확인한다: `brainwash`, `miracle`,
`trojan-horse`, `zugzwang`이 실제로 턴을 종료하는지.

### 발견한 카탈로그 결함

번들의 v2 카드 빌더는 PASSIVE 카드의 `turnPolicy`가 `NOT_APPLICABLE`이 아니면
`Inconsistent v2 card activation`을 던진다. 그런데 우리 카탈로그는 **PASSIVE 18장에
`PRESERVE_TURN`을 기록**하고 있다.

이 필드는 해당 카드들에 대해 **무효**하다. PASSIVE는 획득 시 설치되고 소비할 charge가 없어
`ends_turn`을 읽는 경로에 도달하지 않는다. 그래도 카탈로그가 원본과 어긋난 사실은 남긴다.
`passive_cards_declare_inert_turn_policies` 테스트가 이 18장을 고정해, 조용히 늘어나지 않게 한다.

## 알려진 한계: `premove` 열거 비용

`P0` 동적 목표 열거 작업에서 가변 선택 카드 6장을 전수 조사했다. 5장은 완전 열거로
끝났고, `premove`만 **계약과 성능이 충돌**한다.

`premove`는 1~3개 기물의 이동을 "순서대로" 선언한다. canonical 카탈로그의 selection은
2~6칸, 즉 **완성된 목록**이고 upstream도 `selections.length > 3`으로 완성 목록을 검증한다.
그래서 `legal_actions`가 모든 완성 목록을 물질화해야 한다.

측정값(움직일 수 있는 기물 6개 기준, 58,468개 액션):

| 단계 | 시간 | 비중 |
|---|---:|---:|
| 3수 `declarations` | 223ms | 88.4% |
| `state.clone()` | 12ms | 4.8% |
| `push_action` | 8.3ms | 3.3% |
| 2수 `declarations` | 7.5ms | 3.0% |
| 나머지 | 1.4ms | 0.6% |

3수 호출은 첫 수 49개 × 두 번째 수 평균 38.5개 = 1,887회이고, 매 호출이 남은 4기물의
이동을 생성한다. 그중 **69.1%는 결과가 이전과 동일**하다(9,435회 중 6,524회).

### 왜 지금 구조를 유지하는가

`Action`을 "선언 1개" 단위로 바꾸면 upstream과 같아지고 열거가 58,468 → 7,548로 줄어
약 6배 빨라진다. 대신 네 가지를 잃는다.

1. `premove` 한 번이 액션 1개에서 3개가 되어, 경로당 64개 제한에서 같은 예산으로 보는
   수가 줄어든다.
2. `legal_actions`가 "선언 중"이라는 중간 `GamePhase`를 가져야 하고, 탐색이 "루트 액션 =
   카드 완료"로 가정한 곳이 깨진다.
3. 그 중간 상태를 평가할지 결정해야 하고, 평가하면 노드가 늘고 안 하면 점수가 부정확하다.
4. 웹 UI·기보·fixture가 모두 "액션 하나 = 한 수"라는 전제를 잃는다.

이득은 카드 하나에 국한되고 손실은 탐색 전 구간에 걸치므로, **현재 구조를 유지**한다.
다만 `premove`가 있는 국면에서는 열거만으로 250ms 예산을 넘을 수 있다. 이는 탐색이
반복 심화를 못 하는 구조적 제한이며, 위 수치가 그 근거다.

## 보존할 불변 조건

- 같은 플레이어의 연속 행동에 무조건 부호를 반전하지 않는다.
- 완료 턴은 `TurnEnded`로 센다. 중간 선택에서 행동자가 바뀌는 것과 구분한다.
- live RNG를 탐색의 미래 정보로 쓰지 않는다.
- 미탐색·중단·확률 표본을 안전이나 승패 증명으로 표시하지 않는다.
- 중단 대국의 휴리스틱을 실제 승률 정답으로 쓰지 않는다.
- 학습을 재개할 때 실제로 필요한 행동 표현·관측·데이터 계약만 새로 만든다.
